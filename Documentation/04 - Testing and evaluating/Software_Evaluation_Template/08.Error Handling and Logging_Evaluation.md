# Error Handling & Logging

**Application handles errors gracefully (instead of crashing).**

Has this criteria been met? *Yes*

Analysis: All errors are handled using a try catch block within the code, and a pop up is shown for the user. The app does not crash when it faces errors, but it does ask the user to reload or retry the action they were attempting to execute.

<br>

**Try-catch blocks (or equivalent) are used for handling errors.**

Has this criteria been met? *Partially*

Analysis: Try-catch blocks were definitely used for handling errors. In fact, 17 separate try catch were used. However, they could be used more extensively in error prone errors in order to make 100% sure that the application will handle all errors gracefully.

<br>

**Error messages help the user understand what went wrong.**

Has this criteria been met? *Yes*

Analysis: Error messages briefly describe the issue and direct the user to complete an action, for example, reloading the page or signing in again. The testing and evaluating phase also verified that the error messages do not over-expose system logic.

<br>

**Errors and warnings are logged (for debugging).**

Has this criteria been met? *Yes*

Analysis: After manual inspection, the backend server saves all errors in a log file. Any errors on the frontend are not sent to the backend - this is purely a bad idea, because it would increase the amount of error logs.
