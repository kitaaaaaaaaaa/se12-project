# Software development approach

This page outlines the software development approach used for the project.

## WAgile
The WAgile approach to software development combines the flexibility and product-focused approach of Agile and the structure, clarity and documentation brought by Waterfall. 

During Identifying & Defining and Research & Planning, Waterfall is used comprehensively define requirements. It also makes the project easy to manage in the beginning, creating a solid foundation upon which development can occur.

During Producing & Implementing and Testing & Evaluating, Agile is used, bringing flexibility through its iterative development sprints. This makes development highly adaptable and it is easier to manage. Each sprint provides an opportunity for client feedback and the revision of project requirements if neccessary.

## Why WAgile?
The software engineering project requires an extensive set of documentation, and has loosely defined requirements that may be adjusted at any time due to time constraints. Thus, we must choose an approach that favours both documentation and flexibility.

 Using Waterfall in the first half of the project allows documentation to be written for the assessment. Proper planning and documentation makes the rest of the project easier to manage and execute, saving time in the long run.

Using Agile in the second half of the project means that the project can quickly adapt to unforeseen circumstances if needed (such as time constraints). Previous phases can still be adapted based on what is learnt from each sprint. After each sprint, code optimisation and vulnerability assessments can be done as we go, saving time later on. It allows for continuous collaboration with the client, resulting in a solution that the client is more likely to use. Agile facilitates a cycle of development and testing, avoiding time consuming and costly errors later on.

## Potential Drawbacks
- WAgile requires careful planning in order to integrate these two varying approaches. The development of a GANTT chart allows the integration of these two approaches to be planned beforehand, reducing decision fatigue and wasted time later on.
- Waterfall is traditionally not flexible to changes in requirements. Using WAgile means that requirements can be reviewed after each sprint during development.
- During the Agile phase, the project can become challenging to manage. A Kanban board has been created in order to mitigate this, redirecting mental effort to development and documentation rather than organisation.
