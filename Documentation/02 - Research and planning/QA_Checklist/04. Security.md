# Security – Is it protected against threats?
## User authentication & authorisation are implemented securely.
**What does this mean for my project? (If not relevant, say why.)** <br>
Credentials should be stored on a secured database. Libraries used to hash passwords should be up to date and secure. Front-end must send password to back-end using asymmetric encryption to protect data in transit. Password hashing must be done on the back-end.

**How and when will I check this?** <br>
This will be checked in the early stages of Producing and Implementing, when the authentication system is made. The required elements will be checked for, and a manual vulnerability assessment will be conducted.

## All input fields are validated and sanitized to prevent SQL Injection/XSS/CSRF.
**What does this mean for my project? (If not relevant, say why.)** <br>
Authentication user inputs and run sheet instruction inputs should be validated and sanitised on the front-end. This reduces the amount of API calls and reduces the risk of attacks. User inputs will also be validated and sanitised on the back-end as a second line of defense to prevent SQL injections, XSS attacks and CSRF.

**How and when will I check this?** <br>
This will be checked through manual inspection during the Producing and Implementing phase, after creating the authentication system and the implementation of run sheet instructions in particular.

## Passwords are hashed and not stored in plain text.
**What does this mean for my project? (If not relevant, say why.)** <br>
Passwords stored in the database must not be readable at a glance. They should be hashed using a reputable Python library before being stored.

**How and when will I check this?** <br>
This will be checked through manual inspection after developing the authentication system.
