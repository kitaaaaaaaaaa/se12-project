# Code Quality & Maintainability – Is it clean and scalable??
## Code is modular and reusable (functions, classes, components).
**What does this mean for my project? (If not relevant, say why.)** <br>
User interface is made of reusable components and CSS classes. JavaScript and Python files will utilise reusable functions, classes and objects. This may be custom made, or adapted from a library.

**How and when will I check this?** <br>
This will be checked throughout the Producing and Implementing stage towards the end of the sprint. Manual inspection of the code will be used.

## Follows a consistent coding style
**What does this mean for my project? (If not relevant, say why.)** <br>
The level of indents, curly braces and use of classes/functions should be used appropriately and consistently. For instance, an indent must always be marked by four spaces, or curly braces should always look like this to preserve consistency:
```js
function myFunction1() {
    element1.textContent = "hello";
}

function myFunction2() {
    element1.textContent = "world";
}
```

As opposed to mixing it like this:
```js
function myFunction1()
{  element1.textContent = "hello";
}

function myFunction2() {
    element1.textContent = "world"; }
```

**How and when will I check this?** <br>
This will be checked during the Producing and Implementing stage when writing code. VSCode extensions like JSlint and Pylint will be used to highlight inconsistencies in code style.

## Comments and documentation are provided for key parts of the code.
**What does this mean for my project? (If not relevant, say why.)** <br>
The code should have comments at the top of each function to give a brief description of what the function does and how it works. When using Python, the code should ideally use docstrings to make the function easier to use in the future.

**How and when will I check this?** <br>
It will be checked during the Producing and Implementing phase. A combination of manual inspection and JSlint/Pylint warnings will be used to check this.

## Meaningful commit messages in Git (e.g., "Fixed form validation bug").
**What does this mean for my project? (If not relevant, say why.)** <br>
Every commit made using Git should follow the established [commit conventions](../../journal.md#08042026). The commit messages should accurately describe changes made in an imperative mood. For instance, "Fixed form validation bug" should be "Fix form validation bug" according to the conventional commits specification.

**How and when will I check this?** <br>
This will be checked every time a commit is made. The commit conventions are one of the several documents I always have next to me when working on the project. Every time a commit is about to be made, the commit message is checked to see if it follows conventions.

## The project structure is well-organsised (e.g., src/, assets/, components/).
**What does this mean for my project? (If not relevant, say why.)** <br>
Project files are organised and sorted into folders based on general categories. Resources and assets should be easy to locate, rather than being pooled in one folder. There should be separate folders for the front-end (client) and back-end (server). There should be other folders for assets, fonts, icons and other groupings if CSS and JS files are separated into multiple files.[^1]

**How and when will I check this?** <br>
This will be checked during the Producing and Implementing stage, as it is easier to keep organised throughout the project rather than do it at the end. It will be checked through manual inspection of the project folder structure.

[^1]: Obaseki Noruwa 2023, Folder Structure for Modern Web Applications, DEV Community, viewed 29 April 2026, \<https://dev.to/noruwa/folder-structure-for-modern-web-applications-4d11>.
