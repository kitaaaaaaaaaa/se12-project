# Functionality – Does it work as expected?

## The software meets the initial requirements and objectives
**What does this mean for my project? (If not relevant, say why.)** <br>
The software must have a home page to view different events and their run sheets. Users must be able to create, edit and delete run sheets, before and during the event. Admins should be able to progress the run sheet forward during the event, and crew members should be able to view this progression live. The software must also have an authentication system.

**How and when will I check this?** <br>
The Producing and Implementing stage is centred around sprints. Each sprint will culminate in one functional requirement being built, so the criteria will be fulfilled. If any problems arise after a sprint (e.g. time limitations), the requirements will be checked and revised. Ultimately, it will be checked throughout the project through manual review.

## Features work correctly without crashes or unexpected behaviour
**What does this mean for my project? (If not relevant, say why.)** <br>
All the [essential features](/Documentation/01%20-%20Identifying%20and%20defining/4.%20Functional%20Requirements.md#essential-features) must work in the final software solution. The software must not suffer from unrecoverable crashes, or exhibit behaviour that deviates from the features. This means that my project must use correct algorithm logic and handle errors gracefully.

**How and when will I check this?** <br>
This will be checked throughout the Producing and Implementing stage after the completion of each sprint, to reduce the likelihood of costly errors later on. It will be checked through user testing. The software will be given to the client, and they will try to force a software bug or crash. I will also do the same to combine varying perspectives.

## Forms and inputs validations and incorrect inputs are handled properly
**What does this mean for my project? (If not relevant, say why.)** <br>
User inputs in my project, for example usernames, passwords and run sheet instructions, should check for invalid data in order to prevent unforeseen errors and potential SQL injections. Incorrect inputs should always be rejected (with data validation occuring on the front-end and back-end to stop attackers from bypassing it) and a helpful error message should be shown.

**How and when will I check this?** <br>
Data validation will be checked throughout the production of the software solution, since features are tested at the end of each sprint. It will also be re-checked during the Testing and Evaluating phase, since input validations aren't time consuming to check.

## APIs and third-party integrations (if used) function correctly
**What does this mean for my project? (If not relevant, say why.)** <br>
Third-party integrations will not be used in this project, since none are needed to create this synchronised run sheet. APIs will be used in the form of a back-end Flask server. The front-end must be able to communicate with the back-end, and the back-end must return the correct information.

**How and when will I check this?** <br>
Since the back-end will be developed in conjunction with the front-end, API functionality will be tested throughout the development process.

## Boundary values have been considered and tested
**What does this mean for my project? (If not relevant, say why.)** <br>
The project will not involve boundary values since it won't use any control structures that are based off of integers or floating point numbers.
